## 可直接发送给开发 Agent 的指令

你正在维护已经部署、已经与朋友实际试玩过的 NanoParty。现在实施 VNext“综合体验打磨”。请完整阅读配套 PRD v1.1、仓库 `AGENTS.md`、原 PRD 与当前架构／游戏文档，再核对最新代码。

这不是从零建仓任务，也不是新增十款游戏任务。不要重做已完成的模块，不要因为先前文档说某功能未实现，就忽略当前代码。新 PRD 明确覆盖旧讨论中的冲突；其“建议默认”允许直接采用并记录，不必逐项重新问产品。

### 一、这次真正要做好的体验

1. 固定朋友群持续使用长期房间，每场派对独立计分，连续玩多款小游戏，结束后有完整回顾。
2. 右侧聊天分普通发送与发送并找 AI。当前题主可以通过右侧请求新题，左侧出现能真正选择、确认和继续游戏的题卡。
3. 当前题主不必总找房主代操作；可以刷新、手动出题、回看本场历史候选。没选的题不是废题，下一轮别人还可以选。
4. 海龟汤沿用左侧提问与判断记录，只把执行判定的人替换为独立游戏 AI。右侧房间 Agent 不得读取未揭晓汤底。
5. 搞怪模式是本次重点：像一个能接话的网友，而不是客服。朋友可以争分、讨价还价；AI 可提出离谱方案，但房主确认后才改变派对积分。
6. 本地 Claude Code 能只读拉取生产试玩报告，控制多个测试玩家走真实操作路径，并把问题变成回归案例。

### 二、先核对，再实际开发

先输出一份短的现状差异表，逐模块标记“已有／需完善／缺失”，附关键文件位置。给出分批实施顺序和会影响已有数据的变更。然后直接进入可运行的实现，不停留在又一份长计划。

普通工程选择自主决定。只有破坏性数据迁移、产品权限变更、明显范围扩大、真实新增费用，或者无法同时满足两条需求时，才提出具体阻塞问题；不要重新询问已经确定的产品目标。

建议按以下闭环交付，可根据实际依赖调整顺序：

- 第一批：最小反馈／测试支撑，双发送入口，题主权限，候选选择、刷新、历史与 AI 联动。
- 第二批：海龟汤 AI 裁判、母题约束改编、纠错与失败恢复；搞怪主持和动态多人交互的真实模型验证。
- 第三批：长期房间与独立派对、名次奖励、可选协商调分、完整回顾、偏好调整与视觉统一。
- 最终：Docker／旧数据迁移验证，多浏览器回归，生产报告回流和朋友试玩验收。

分批不等于省略需求。尤其完整回顾、真实模型验证和开发测试工具，不能用静态示例或一句“接口已预留”代替。

### 三、不可误读的边界

**正式游戏操作留在左侧。** 海龟汤提问不是右侧聊天消息；右侧处理自由需求与派对协商。两种 AI 可以共用模型服务，但不共用秘密上下文。

**基础人格与模式不同。** 普通与搞怪都自然、年轻、适度玩梗；差别在提议的大胆程度，不在是否有权越权。不要把搞怪实现为高频插话或随机加分。

**原始成绩与派对积分分离。** 每个小游戏正式结束后按名次奖励。合作游戏保留客观记录并允许即兴协商，不构建繁重的贡献权重算法，不强制人人互评。协商可以产生负分；必须显式批准、一次生效、有流水。

**候选展示不等于已使用。** 历史跨回合可用；秘密内容受游戏权限限制；题目确认之后不能被迟到的 AI 请求覆盖。

**内容按来源处理。** 公开数据要答案快照与出处，朋友偏好要当事人预答，创意题不硬套事实校验。海龟汤以高质量母题与受限改编为主，不靠每局零样本生成。

**Dynamic Canvas 是有状态的交互。** 至少完成一次 Agent 组合输入、投票和选择的多步骤用例；不必生成任意网页代码，也不能只是展示一张没有后端结果的卡。

**现有固定游戏照常工作。** 不要求牛头王等固定规则游戏都接入选题或 LLM。无模型保留基础玩法；AI 海龟汤则明确提供人工主持等降级。

**不要扩大本次范围。** 不做外部大棋盘、RPG 属性、道具技能、语音识别、主持人入场动画、在线编程沙箱或公共平台。

### 四、工程与验收要求

沿用现有架构的可用边界，提供安全迁移，不清空生产记录。新规则用版本标识；旧版原始分累计数据不能被无声转换为新名次积分。新增秘密信息不能出现在公共视图、Agent 工具返回、日志或回顾中。

保留单元测试，但必须额外完成：多身份协议流程、多隔离浏览器 UI、权限反例、恢复与幂等、真实模型用例。Mock 与真模型分开标注；没有密钥或访问条件时，相关验收写“未执行”，不要宣称通过。

给 AI 测试员提供批量动作与简洁摘要；截图、trace、完整日志按需获取。不为每个虚拟玩家调用 LLM。调试身份切换和全知断言只在测试环境，生产必须拒绝访问。

生产数据回流先做按需、只读、脱敏的 SSH 导出／拉取流程；不开放生产数据库公网端口，不自动把全部聊天或密钥送入模型，不覆盖本地开发数据库。

### 五、每批交付给我什么

交付实际修改与可运行功能，并简要报告：

- 对应 PRD 需求编号与验收编号，完成／未完成情况。
- 执行的命令、测试结果、浏览器与模型证据位置。
- 本次采用的建议默认值、迁移方式与升级步骤。
- 仍存在的问题、需要我提供的密钥／SSH／试玩条件。

请以配套 PRD 第 14 章作为最终验收清单。开始前先核对仓库状态，随后推进实现；不要再把产品讨论完整重开一遍。
