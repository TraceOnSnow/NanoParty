# ADR 0005：Dynamic Canvas = 固定交互原语 + Agent 自主编排

状态：已采纳（2026-11-14）

## 背景

产品方向更新：Agent 应能根据玩家的自然语言要求，在主面板组织多人交互，并让结果真正作用于游戏，而不是只执行开发者预先写好的流程。候选方案：

| 方案 | 自由度 | 复杂度 | 多人同步与秘密隔离 | 安全 | 持久化与恢复 |
| --- | --- | --- | --- | --- | --- |
| A. 预定义原语 + Agent 编排 | 流程自由，外观固定 | 低 | 由程序保证 | 好 | 简单 |
| B. 声明式 UI Schema（布局树） | 外观也自由 | 中高 | 每个节点都要定义可见性 | 中 | 需给整棵树做版本兼容 |
| C. 生成前端代码 | 最高 | 很高 | 无法保证 | 差（会话令牌在浏览器里） | 很难 |

## 决定

采用 A。长期方向是 B，可以通过「一个页面 = 若干文字块 + 原语」逐步过渡，不需要改持久化模型。

- **原语**：`collect`（每人一句文字）、`choose`（多人即投票，单人即挑选）、`show`（只展示）、`confirm`（只由程序创建，包着一个待批准的效果）。规格是经 zod 校验的声明式数据，不含布局，也不含可执行内容。
- **交互对象**（`interactions` 表）：规格、谁能回应、各人的回应、结构化结果，状态 queued → open → closed。服务重启后原样恢复。
- **时机**：交互只在「安全点」打开——没有游戏、或游戏声明的回合间隙（`GameModule.atSafePoint`）。回合中提出的请求，Agent 在后台照常处理，生成的交互排队等待。
- **闭环**：交互结束 → 程序计算结果、写库、在群聊留摘要 → 若由 Agent 创建，则带着结果再次唤醒 Agent → Agent 决定下一步。Agent 用 `note_plan` 记住多步流程的计划。
- **效果工具**（有类型、有限）：`save_content`（按内容类型校验后入库，来源标为 AI 生成）、`offer_content`（交给游戏，由游戏的 `offer` 决定怎么用）、`suggest_game`、`propose_start_game`。需要授权的效果在创建确认时就固定下来，批准后由程序执行，模型不再参与决定；确认面板上的说明由程序生成。
- **游戏接口扩展**（全部可选）：`atSafePoint`、`offer`、`GameContext.peekContent / consumeContent`（候选题只看不用、确认后才计为已用）、`GameResult.contributed`（玩家自拟内容入库）。
- **护栏**：每房间同时最多一次模型调用；没有人类请求时，Agent 最多连续自动进行 6 步，之后停下并提示玩家 @AI。

## 与原 PRD 的差异（已与产品确认）

- PRD 规定模型只在 @AI、点击或预设重要事件时调用。「Agent 创建的交互结束」被视为预设事件，并受上面的步数上限约束。
- 匿名提交暂不实现（朋友局，大家和 Agent 都能看到作者）。

## 验证

- 服务端测试用脚本化模型驱动「收集 → 投票 → 写候选题 → 交给游戏 → 玩家挑选」，并覆盖重复提交、过期交互、批准只执行一次、重启恢复、步数上限。
- **尚未用真实模型验证** Agent 是否真的能自己规划这些流程；脚本化模型和开发用的模拟模型只证明管道可用。
