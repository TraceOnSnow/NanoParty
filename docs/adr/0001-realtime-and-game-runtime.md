# ADR 0001：Colyseus 做实时房间层，游戏规则用自有的纯函数内核

状态：已采纳（2026-11-13）

## 背景

PRD §10.3 要求在 boardgame.io（优先考察）与 Colyseus（备选）之间验证后选型，重点验证：同时提交、秘密信息、服务端推进、恢复、跨游戏切换。

## 验证结果

两者都用最小脚本实测（同时隐藏提交 → 统一揭晓）。

| 关注点 | boardgame.io 0.50.2 | Colyseus 0.18 |
| --- | --- | --- |
| 维护状态 | 最后发布于 2022-11，已基本停更 | 活跃（本月仍在发布） |
| 同时提交 | 可行（`activePlayers` + stage），实测通过 | 可行（消息处理器自行实现），实测通过 |
| 秘密信息 | `playerView` 过滤，实测通过 | 不用 Schema 同步，按连接发送过滤后的视图，实测通过 |
| 服务端推进（超时） | 无服务端计时器/系统动作，需要绕路 | 房间内可直接定时并改状态，实测通过 |
| 房间内切换游戏 | 一个 match 绑定一个游戏；房间、聊天、跨游戏积分都得在它之外另建一层 | 房间与游戏解耦，实测通过 |
| 恢复 | 有存储适配器，但 Postgres 适配器为社区维护且同样陈旧 | 不内置持久化，需自行存取（实测：从快照重建房间通过） |
| 其它 | 自带 Koa + 旧版 socket.io、React 绑定较旧 | 鉴权钩子、带确认回执的消息、连接管理齐全 |

验证中还发现：Colyseus 把 `roomId` 作为保留参数，按它过滤会被忽略，导致不同房间被合并——因此用 `partyId` 作为过滤键，并有跨房间隔离测试。

## 决定

- **Colyseus 只作为实时房间/传输层**：连接、鉴权钩子、消息与回执。不使用它的 Schema 状态同步。
- **游戏规则用自有的轻量内核**（`GameModule`，见 `packages/shared/src/game.ts`）：纯函数 + JSON 状态 + 按玩家过滤的视图。这借鉴了 boardgame.io 中验证有效的思路（纯函数 move、`playerView`），但不依赖已停更的库。
- 房间权威逻辑放在与传输无关的 `RoomRuntime` 中；`PartyRoom`（Colyseus 适配层）保持很薄。

## 理由

- 本项目最难的部分（房间跨游戏存续、Postgres 持久化与重启恢复、幂等、AI 经受控工具操作）两个框架都不提供，都要自己写。框架真正能省的是传输层，Colyseus 在这方面更完整且在维护。
- 不用 Schema 同步：规则保持纯函数、可单测；状态原样 JSON 入库；秘密隔离只有 `view()` 一个出口。代价是每次变更发送完整个人快照——在 ≤8 人、状态很小的前提下可以接受。
- 内核接口很小（约 10 个成员），不是通用规则 DSL；每款游戏自己写状态机。

## 后果

- Colyseus 仍在 0.x，升级可能有破坏性变更；因为适配层只有一个文件，替换或升级的影响面小。
- 若将来出现状态很大或高频更新的玩法，再为该玩法考虑增量同步，不提前做。
