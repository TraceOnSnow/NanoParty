# NanoParty VNext｜产品需求文档

**PRD v1.1 · 2026-11-14**  
版本主题：熟人聚会体验、搞怪 AI 主持与开发反馈闭环  
交付对象：项目负责人、开发 Agent、测试与验收人员  
项目仓库：https://github.com/TraceOnSnow/NanoParty

> 版本目标：让同一群朋友愿意反复打开 NanoParty；游戏能顺畅进行，AI 能接话、出题和组织真实互动，朋友之间的即兴发挥能够留下结果，而不是只得到一段聊天回复。

## 0. 文档效力与使用方式

本文是对 `AI_Party_Room_PRD_v1.0.md` 的增量更新。原有自托管、邀请访问、2–8 人房间、确定性游戏规则、持久化与无 AI 基础玩法继续有效；冲突处以本文最后确认的产品方向为准。

**已确认**表示用户已作出的产品决定。正文未标注为建议的产品行为，按本次交付要求执行。**建议默认**是为消除实施歧义补齐的方案，允许研发采用并在交付中列出，不得表述为用户已逐项批准。**长期愿景**不属于本次开发任务。

现有功能应先与当前仓库核对，再按“已完成／需完善／未实现”处理。本文不要求重写已经可用的十款游戏，也不以早期仓库快照判断当前代码状态。具体游戏名称与规则以当前实现和游戏规格为准。

文档导航：第 1–3 章定义版本范围与派对流程；第 4–7 章定义 AI、题目与权限；第 8–9 章定义结算与回顾；第 10–13 章定义反馈、测试和工程交付；第 14–15 章用于验收与默认值确认。

## 1. 版本目标与范围

### 1.1 服务对象与成功标准

首先服务作者与固定朋友群的真实聚会，其次才是整理成便于其他人自部署的源码公开项目。当前主要使用电脑浏览器、外部语音；不接收或分析外部语音，不假装听见笑声、讨论和情绪。

本版重点是搞怪模式下的真实互动。AI 偶尔接错梗、说出离谱提议，可以成为乐趣；机械复述、客服口吻、连续长篇总结、只有口头承诺而没有实际操作，是需要改进的问题。游戏状态错误、未经授权改分、泄露谜底与丢失进度，不属于可接受的“搞怪”。

以完整朋友局和真实模型测试验收，而非仅以功能数量、单元测试数量或模型回复“看起来合理”验收。

### 1.2 本版必须交付

| 模块 | 交付结果 |
| --- | --- |
| 房间与派对 | 长期房间、独立派对计分、连续小游戏、大厅调整偏好、完整派对回顾。 |
| AI 交互 | 普通发送与发送并呼叫 AI；搞怪主持优先；聊天请求能产生可操作面板和结果。 |
| 选题与内容 | 候选选择、刷新、手动出题、AI 出题、跨回合历史、当轮题主权限、共同兴趣适配。 |
| 海龟汤 | 沿用左侧问答界面，增加独立 AI 裁判；固定谜底、受约束改编、纠错与失败恢复。 |
| 结算 | 游戏原始成绩与派对积分分离；名次奖励；合作贡献参考；可选即兴协商与授权改分。 |
| 开发反馈 | 生产试玩报告按需只读拉取；局内反馈可定位；单人多玩家测试；AI 可使用的真实链路验收。 |
| 基础视觉 | 统一大厅、封面、按钮、等待和错误状态；电脑端主流程清楚，不开展全站重设计。 |

### 1.3 明确不做

不新增一批游戏；不做大棋盘、完整 RPG、跨游戏道具技能体系；不做小天使入场动画或世界观包装；不做通用成员提及；不做语音转录、录音或音乐玩法；不做公众 SaaS、公开匹配或复杂账号系统。

不做运行时任意前端代码执行、在线编程沙箱或通用游戏规则 DSL；不要求每个游戏都使用通用 Canvas。不得为追求“AI Native”把成熟按钮操作全部替换成对话。

共同兴趣和朋友题可以由玩家当场提供，但本版不建立私人知识库，不接入全量聊天记录，不要求 Steam、B 站或游戏账号连接后才能游玩。

### 1.4 分批交付不等于删减范围

可以分批提供可试玩版本，先验证搞怪主持、选题与海龟汤，再完成积分、完整回顾和工具链。任何阶段演示都必须说明未完成项；完整回顾已被选择为正式需求，不能降为“以后再做一段 AI 总结”。

## 2. 房间、大厅与派对生命周期

### 2.1 产品对象

| 对象 | 含义与保存范围 |
| --- | --- |
| 房间 Room | 长期空间；邀请入口、身份恢复、房间偏好模板和历史派对。 |
| 派对 Party／Session | 一次聚会；自己的参与者、主题、主持模式、小游戏记录和派对积分。 |
| 小游戏场次 Segment | 连续游玩一个游戏的单位，可包含多个回合；正式结束时结算派对积分。 |
| 回合／局 | 按游戏定义；一题、一墩牌、一次完整发词局不强行统一。 |

**LIFE-01｜独立计分。** 同一房间同一时刻最多有一场进行中的派对。新派对从零计分；旧派对存档，不覆盖。退出浏览器、掉线、跨日、全部玩家暂离均不自动结束派对。

**LIFE-02｜成员。** 使用已有浏览器凭据恢复身份，昵称不是认领凭据。新加入者只计实际参与场次，不对历史积分归一化；各游戏在安全阶段接纳新玩家，不把中途加入者塞入已分配秘密的当前局。

### 2.2 大厅布局

沿用电脑端左右布局。左侧为大厅或当前游戏；右侧为本场派对积分与房间群聊。大厅主要区域依次为当前派对状态、参与者与连接情况、轻量偏好摘要、游戏卡片。历史派对、结束派对和房主管理放在次级入口。

**LOBBY-01｜直接开玩。** 游戏选择与“调整派对偏好”并列；偏好不是开始游戏的前置条件。游戏卡片显示名称、机制简介、人数要求、AI 依赖与可玩状态。人数不足显示原因，不只显示一个灰按钮。

**建议默认：** 没有活动派对时，房主首次选择游戏可同时创建派对；也提供明确的“开始新派对”入口。创建过程不能让两个并发点击产生两场活动派对。

**LOBBY-02｜全局保留。** 小游戏结束返回大厅，玩家身份、聊天、偏好和本场积分保留。右侧显示正式派对积分，游戏内原始分数在左侧显示；尚未结算的奖励只能标作预计值，不能混入总榜。

### 2.3 结束与恢复

**LIFE-03｜两种结束。** 小游戏提供“结束并结算”和“放弃本场”两个含义清楚的操作。无限轮模式必须能在完成至少一个有效计分单元后正常结算；不能因为房主主动结束就一律认定放弃。正在进行但未完成的回合，需要明确确认舍弃，不回滚此前已完成回合。

**LIFE-04｜结束派对。** 房主在大厅确认结束；存在进行中的小游戏时，先完成／结算或明确放弃。结束后冻结正式记录，展示完整回顾。模型总结不阻塞冻结、排名或开始下一场派对。

**LIFE-05｜异常恢复。** 断线恢复当前玩家和页面状态；服务重启恢复已确认提交、候选、待处理交互和结算状态。建议恢复后暂停游戏计时，由房主继续，不将停机时间算作玩家超时。

**建议默认：** 房主短暂离线不自动转移权限；提供显式转交与管理员恢复入口。不能因多人声称“我是房主”自动更换；本版不做复杂自动选举。

## 3. 派对偏好与共同兴趣

**PREF-01｜同一入口。** 大厅中的“调整派对偏好”与首次准备使用同一流程。可进入、取消、重新调整；不清积分、不重置身份、不新建派对。保存后影响后续内容，不改已确认题目。

**PREF-02｜轻量共建。** 玩家可以勾选、输入少量标签、表达熟悉程度和想玩方向。AI 可以给候选方向，玩家再具体化；不是强制问卷。明显冲突时展示选择或让房主确认，不用最后一句话覆盖全体偏好。

偏好至少区分“熟悉什么”“今天想玩什么”“不要出现什么”。例如熟悉英雄联盟但今天想换口味；不熟悉某话题不等于永久屏蔽。建议保留本场主题、排除项、内容难度与主持模式，并可沿用上次配置。

**PREF-03｜内容取向。** 默认不满足于通用冷知识。支持主播与视频数据、游戏细节、朋友主动提供的战绩或偏好等主题。比如“某个视频在指定时间的播放量”“某位朋友上周用了多少次某英雄”“当事人最喜欢哪个炸鸡部位”。这些是出题方向示例，不代表系统已经知道答案。

**PREF-04｜即时共创。** 主要支持游玩中突然提出想法：玩家给方向，AI 提供具体题目；玩家继续修改；确认后进入游戏。保存被选中、使用或收藏的好内容；未使用候选留在本场历史，不等于自动发布为全局优质题库。

## 4. 右侧聊天、AI 主持与模式

### 4.1 入口与响应

**CHAT-01｜两种发送。** 同一个输入框提供“发送”和“发送并找 AI”两个清晰入口。普通发送只进入群聊；后者公开消息并触发房间 Agent。保留手动 `@AI`，但不要求用户记住它，也不开发通用 `@成员` 列表。

建议 Enter 普通发送、Shift+Enter 换行；AI 使用独立可见按钮，快捷键作为可选增强。请求通过结构化意图触发，不靠在消息正文中伪造用户名或权限。

**CHAT-02｜明确结果。** 展示排队／处理中／完成／失败状态。AI 只有在工具真正成功时才能说“已更新”；需要确认时说“已提出，等待确认”。重试不能重复改分或重复发布交互。

**CHAT-03｜群聊节奏。** 普通聊天保留为后续上下文，不逐条调用模型。短时间多个请求可以合并；有冲突时澄清或给选项。基础串场可按事件触发，但不要求每个回合都评价、总结、询问满意度。

### 4.2 同一基础人格，两种行为模式

**HOST-01｜基础人格。** 两种模式都像年龄相近、懂游戏与网络文化、能正常接话的网友。默认短回应，贴合当前语境；不堆流行语，不强行夸奖，不反复复述用户需求，不每次以“友谊第一”收尾。

**HOST-02｜搞怪优先。** 本次朋友试玩优先验证搞怪模式。它更愿意接争分、讨价还价、荒诞理由与意外提议，可以适度反驳和自嘲。普通模式偏向原规则和可预测安排；不是“普通严肃、搞怪才幽默”。

模式影响提议倾向与对边界玩法的接受程度，不直接扩大执行权限。搞怪模式不等于随便改数据库、忘记已经接受的约定，或让海龟汤裁判故意错判。

对话风格示例，仅用于说明而非固定模板：玩家说“这把我纯 C，至少加五分”，AI 可以接当前事实、反驳或顺势谈条件，然后提交一个真实可确认方案。不能捏造“你刚才说过某事”来制造笑点，也不能凭空声称听到了语音内容。

### 4.3 房间 Agent 与游戏 AI

**HOST-03｜独立上下文。** Room AI 负责聊天、偏好、选题协助、Canvas 和协商。Game AI 负责海龟汤判定等特定任务。可以共用模型网关，也可以分模型、Prompt、预算和日志；不要求采用多 Agent 框架。

房间 Agent 只获得允许公开的信息；海龟汤裁判可以读取固定汤底，但只返回受控判定。生成秘密答案的工具应向房间 Agent 返回内容 ID 与安全摘要，而不是把答案塞进公共对话上下文。

**HOST-04｜成本与容错。** 选题刷新优先题库，不每次请求模型；自动化回归默认假模型，真实模型单独验收。超时、额度耗尽、取消和过期结果均有可见状态，正常游戏操作不能等待房间 AI。

## 5. 候选题、AI 出题与历史

### 5.1 左侧选题流程

**CONTENT-01｜同一候选区。** 适用游戏增加独立的选题准备阶段：默认候选 → 当前题主选择／刷新／回看／手动出题 → 确认 → 正式游玩。固定牌类游戏不需要硬加选题流程。

左侧提供“当前候选”“历史候选”“换一批”“自己出题”“确认使用”。AI 自由要求在右侧输入，结果更新左侧；不再增加第二个通用聊天框。按钮可以聚焦右侧输入并带上游戏上下文。

**CONTENT-02｜刷新不是跳题。** 选题阶段不设固定刷新次数，不扣分、不轮换题主、不消耗正式回合。刷新优先读取本地题库与已生成缓存；题库用尽时允许回看、重复候选、手动出题或等待生成。正式游玩后的换题按跳过／作废规则处理，不偷偷替换已有答案。

建议默认展示 3 张候选；数量由具体请求或游戏配置决定。候选刷新不能顺便重抽已确定的秘密目标、身份或牌。正式计时从该玩法规定的确认点开始，不能靠刷新反复重置已开始的作答计时。

**CONTENT-03｜当轮权限。** 当前题主可以在其合法阶段选择、刷新、手动出题、确认。房主无需代点，但保留明确的管理覆盖能力。其他玩家可查看允许公开的候选并提出建议，不能抢先确认或悄悄覆盖题主选择。

### 5.2 AI 与候选区联动

**CONTENT-04｜生成与发布分离。** 右侧发出“给我三道魂系相关题”，AI 获取当前游戏、题目格式、请求者身份与选题阶段；通过工具生成有效候选并发布。每张卡通过结构校验后才可操作，不渲染未完成的模型文本为正式内容。

题主发起且仍处于同一选题阶段时，新批次可成为当前候选；其他人的请求默认进入建议区／历史，由题主接受。原有候选不被删除。模型失败保留可用题目；玩家在等待期间仍可选旧题。

若题主已确认、游戏已切换或新请求取代旧请求，迟到结果不能覆盖活动题面。可保留到所属派对、对应内容类型的历史中，并明确“未应用”；不可跨派对发布。

### 5.3 候选历史

**CONTENT-05｜展示不等于使用。** 题卡至少区分未使用、选中待确认、正式使用／已玩、跳过／作废。取消选择不消耗题目；换一批只切换展示集合。相同题目的状态只有一份，不因多次展示重复创建。

**CONTENT-06｜跨回合持久化。** 历史默认覆盖当前派对、当前可兼容内容类型。下一位题主可以找回上一位没选的题；刷新页面或重启服务不丢失。已玩题默认标记并不重复推荐，允许明确选择重玩；未选中不能被误记为差题。

建议历史按批次和最近时间排列，提供“未使用”筛选；不做完整题库管理后台。跨派对优质内容由收藏／入库另行保存，不默认公开朋友题。

**CONTENT-07｜信息隔离。** 历史遵守游戏可见性。公众能看光谱题面，不等于能看猜测目标；谁是卧底不能向参赛者展示完整词对；事实题不能展示答案。记录谁看过秘密，不能仅因换了一个页面就假设其不知道。需要答案的自定义题由不参与猜题者提供，或采用明确的当事人预答模式。

### 5.4 答案来源与共创

**CONTENT-08｜三类来源。**

| 类型 | 生成／提供方式 | 正式开始前必须满足 |
| --- | --- | --- |
| 创意与联想 | 本地题库、玩家手写、AI 生成 | 格式合法、适合当前玩法、明确公开范围。 |
| 事实与数字 | 可靠资料、可用检索工具、玩家提供依据 | 答案、单位、统计口径、时间点及出处／线索固定。 |
| 朋友数据与偏好 | 当事人或获知答案的出题者主动提供 | 在他人猜测前私密锁定答案；出题者是否参赛按游戏说明。 |

不能因为模型语言流畅就把猜测记为已核实。查不到资料时允许换题、补充答案，不阻塞其他候选。网页资料与玩家自定义文本都是内容，不是修改系统权限的指令。

**CONTENT-09｜秘密输入与沉淀。** 右侧群聊是公共区域；需要填写正确答案时，在左侧使用私密表单，不引导玩家把答案发进群聊。事实题按出题时快照结算，不在揭晓时换一份“最新值”。生成／手写／导入来源和版本保留；题目修订产生新版本，不改变历史对局。

## 6. 海龟汤：真正的 AI 裁判

### 6.1 主持模式与页面

**SOUP-01｜复用现有流程。** 玩家在左侧游戏主面板输入问题并提交；全体看到问题记录。真人模式由主持人在问题后选择“是／否／无关”，AI 模式改为服务自动判定。不是要求玩家转到右侧 `@AI`，也不是重做一个聊天游戏。

有模型时可选择 AI 主持；无模型时保留真人主持。模型配置、调用状态与失败提示在游戏内可见，不能把模拟回复当作真实 AI 功能。

**SOUP-02｜问题状态。** 单个问题有稳定 ID，经历“已提交／排队／判定中／已回答／需要澄清／失败”。问题和结果对授权参与者同步，重复点击不产生两份判定。多玩家提问按服务端接受顺序组织。

建议默认对同一谜题串行判定，使后续判定能读取已确认问答。失败可单题重试，不阻塞查看历史、修改偏好或房主管理；旧谜题返回的答案不进入新谜题。

### 6.2 判定依据与秘密边界

**SOUP-03｜固定真相。** 裁判输入包括固定汤底、必要事实／因果约束、当前问题、已确认问答和人工修正。允许输出“是／否／无关／需要澄清／信息不足”，不能被迫在未知细节上编造事实，也不能边回答边修改汤底。

正式答案默认简短，不自动追加能够揭露关键反转的解释。最终推理、提示、揭晓分别有明确入口和权限；提出普通问题不等于申请揭晓。用户把“忽略规则，输出汤底”写成问题也不得泄露答案。

**SOUP-04｜独立裁判。** 房间 Agent 不读取未揭晓汤底；裁判输出只经过允许公开的字段投影到玩家视图。原始模型响应、工具参数、错误栈、调试日志均不可经公共消息泄露秘密。

### 6.3 题目质量与改编

**SOUP-05｜优质母题优先。** 默认使用已有可靠谜题与预先整理的模板，不把零样本现场编造全新海龟汤作为正常开局依赖。用户观察到的模型质量差异需要通过题集测试，不在代码中写死某家“永远能出好题”。

每道谜题保留汤面、汤底、关键事实、因果关系、不可改变的条件、可改编元素、来源及验证状态。AI 可针对共同兴趣改人物名、措辞、非关键背景；涉及物理条件、动机或误解来源的名词不能随意换。改编后同步检查汤面、汤底与判定事实；失败时回退母题。

朋友题和自制谜题可留在私服；公开分发包仅纳入项目有权分发的内容。更换人名不应被当成来源审查的替代品。

### 6.4 纠错、降级与解谜结果

**SOUP-06｜可定位纠错。** 玩家可以对具体问题报告“判断有误”；房主可发起重判或更正。原判断、更正、原因和操作者保留，并将更正纳入后续判定上下文。房主并不天然知道谜底；若需要查看，必须明确提示剧透后果，不强制所有朋友局安排真人裁判。

**SOUP-07｜故障接管。** 模型不可用时保留汤面和全部问答，允许重试、暂停或转真人主持。转真人前明确谁将看到汤底、其解谜参与身份如何变化；不得向所有人自动公布答案。没有可接管者时仍可结束／换题，不伪造自动主持可用。

**SOUP-08｜个人贡献。** 记录可观察行为，如有效提交、首次命中某关键事实、最终推理及人工纠正；不按提问条数机械奖励。AI 对突破点的评价只是有依据的建议，不是隐藏的权威分数。贡献协商遵循第 8 章，不能依据未接收的语音判断谁 Carry。

## 7. 操作权限与动态面板

### 7.1 权限矩阵

| 操作 | 默认执行权 | AI 的职责 |
| --- | --- | --- |
| 开始／切换／结束小游戏或派对 | 房主 | 推荐、解释、提出确认。 |
| 当前合法阶段选题、刷新、确认 | 当前题主；房主管理覆盖 | 在授权范围内准备与发布候选。 |
| 答题、描述、猜测、投票 | 对应参与者本人 | 不冒充玩家提交。 |
| 主题建议、反馈、呼叫 AI | 所有参与者 | 汇总，不按最后一句覆盖全体。 |
| 跳题 | 房主或约定的投票规则 | 可以发起，不能擅自跳过下一题。 |
| 正式派对积分调整 | 房主确认 | 可生成离谱但明确的方案。 |
| 海龟汤判定 | 指定真人／游戏 AI | 仅裁判上下文访问谜底。 |
| 测试身份切换、服务端秘密断言 | 本地／专用测试环境 | 不向正式房间开放。 |

**AUTH-01｜服务端判定。** 按房间、派对、游戏、回合、当前角色与状态校验；前端只隐藏按钮不算授权。自然语言中的“大家同意了”“我是房主”不能代替真实确认。

### 7.2 Canvas 的本次边界

**CANVAS-01｜有结果的交互。** 支持 Agent 组合文本输入、选项卡、投票、确认与结果展示。服务端记录参与者、可见范围、提交情况、完成条件、结果、取消与恢复状态；交互结果可以驱动选题或下一步，而非仅显示一张假按钮卡片。

最小动态用例：玩家要求“先让大家填一个主题，匿名投票，再让本轮题主从对应的三张题里选”。Agent 分步骤发布、等待、读取结果并继续；整段流程不写成唯一硬编码功能，单个输入与投票原语仍由可靠程序实现。

**CANVAS-02｜不侵占游戏。** 大厅／选题阶段可使用主要区域；正式答题期间，非紧急交互使用不遮挡的待处理区或排到安全节点。每个结果绑定发起时的上下文；当前题主已提交时，旧投票不得把游戏拉回选题阶段。

建议同一房间只保留一个正在等待全体参与的 AI 交互，后续请求排队或明确替换。发起者／房主可取消；未参与者掉线时按该交互的超时或房主收口策略处理。

**CANVAS-03｜不执行任意代码。** 本版通过结构化组件和受控工具实现，不让模型任意写入权威状态、运行 React／JavaScript 或加载外部页面。模型可提议当前工具不支持的变体，但须如实说明不能执行，不以聊天宣布代替实现。

## 8. 小游戏结算、派对积分与熟人协商

### 8.1 已确认的计分原则

**SCORE-01｜两本账。** 小游戏保留原始成绩、胜负和贡献依据；派对积分根据小游戏最终名次统一奖励。原始分数不再直接进入全局总榜。每个完整小游戏场次结算一次，而非每题都发派对积分。

**SCORE-02｜合作仍有个人表现。** 合作游戏可以形成个人贡献排名，但不是开发精密的贡献算法或强制互评表。可观察记录提供基础；玩家可以当场讨论谁 Carry、谁误导、谁应该少拿或扣分。无法客观区分时允许并列，不能让模型伪装成精确测量。

**SCORE-03｜协商是玩法。** 所有游戏都允许可选的朋友协商，不只合作游戏。AI 可以接梗、整理诉求、提出补偿或离谱奖惩；最终由房主明确确认，不要求每个人强制投票。普通／搞怪模式影响提议方式，不改变授权链。

### 8.2 默认计分口径（建议默认，可配置）

对实际参与并具备结算资格的 N 名玩家，按游戏自身规则形成排名；低分优先、团队结果等由游戏模块解释，不由平台猜测。淘汰者仍是参与者，旁观者和真人谜题主持人默认不参与解谜排名。中途加入／退出按该游戏有效参与规则处理，不因掉线抹掉已获得的成绩。

**建议默认奖励：** N 为 2–8，名次 r 的派对奖励为 `round(10 × (N-r) / (N-1))`。2 人为 10、0；4 人为 10、7、3、0；8 人为 10、9、7、6、4、3、1、0。此数表不是用户已经拍板的分值；应集中配置并标记计分版本，不散落到各游戏。

**并列：** 平分所占名次的奖励均值，统一保留 1 位小数。例如 4 人场中两人并列第一，均获 (10+7)/2 = 8.5；其余为 3、0。不随机拆开同分，也不让 AI 按口才破除并列。

胜负阵营可输出并列名次组；合作贡献缺少足够证据时默认同名次并展示“尚无可靠区分”，玩家可协商。N 小于 2 的非正常场次默认不产生名次奖励。正常多人玩法不因此强制支持单人。

### 8.3 结算页面与操作

**SCORE-04｜标准结果先出现。** 正式结束后，左侧显示原始成绩／可观察贡献、基础名次、预计派对积分，以及“接受并返回大厅”。右侧保留聊天。无需等待 AI 评论或所有人互评即可结束。

**SCORE-05｜可选协商。** 玩家在右侧点击“发送并找 AI”，提出加分、扣分或重分建议。AI 在左侧展示方案：作用于哪场、涉及谁、基础奖励、额外调整、最终增量、理由、待确认状态。只有房主可以确认；房主也有不依赖模型的手动调整入口。

调整支持正数与负数，不把所有玩家最低锁为 0，也不设只能 ±2 的产品限制。仍需有限数值、显示精度和技术安全上限，不能接受 NaN、无限大或溢出。大幅调整给出明确预览，不擅自缩水。

**SCORE-06｜一次确认，一份结果。** 房主可以接受默认方案、批准协商方案或取消协商。正式积分在最终确认时入账，所有玩家收到同一结果；没有批准的 AI 提议不入账。后到方案、重复回调、双击与重连不重复执行。

### 8.4 记录、纠错与结束边界

**SCORE-07｜保留事实与玩笑的区别。** 原始游戏成绩不被争分覆盖；基础奖励、协商调整、理由、提议者与批准者分别保存。调整在回顾中展示为“房主批准的派对调整”，不能变成“AI 已证实某人坑队友”。

**SCORE-08｜追加修正。** 派对仍进行时，可对已结算场次发起更正，以追加流水抵消／补充分数，不改写旧流水。派对结束后正常入口只读；结算前提醒处理未确认方案，用户也可明确放弃未确认方案并结束。

**SCORE-09｜终止与缺席。** 完整有效场次正常结算；主动放弃不发基础派对积分。无限轮数的“结束并结算”使用已完成的计分单元。具体游戏没有可结算结果时说明原因，不能为方便凑出排名。重复玩同一游戏不限制次数，不设计竞技式反刷分。

## 9. 完整派对回顾

**RECAP-01｜完整内容。** 派对结束页与历史入口必须包含最终排名及总分、每场小游戏的参与者与原始结果、基础奖励与协商调整、积分变化过程、关键公开事件、AI 总结及其生成状态。全场结果并列按并列显示。

**RECAP-02｜可靠底稿。** 胜负、逆转、提问与调分等描述来自实际事件；无法从数据判断的“最搞笑”“全场 Carry”只作为玩家评价或 AI 文案，不伪造客观统计。未采纳的提议不写成已发生事件。

**RECAP-03｜异步总结。** 排名与战绩立即可看；总结后台生成，可重试。模型不可用时仍显示完整结构化回顾和记录摘要。开始下一场不等待总结；迟到总结归档到原派对，不插入新派对主持上下文。

**RECAP-04｜秘密与分享。** 只取已允许公开的事件。未揭晓／被放弃谜题的答案不自动进入回顾；朋友题默认只在对应房间可见，不生成公开分享链接。右侧聊天长期保留但按派对分段，AI 默认使用本场上下文及明确保存的偏好，不自动扫全部旧聊天。

**RECAP-05｜历史不重置。** 从回顾返回房间，可查看历史或开新派对。沿用主题不等于沿用积分；新场记分、未完成交互和候选状态独立。房间长期存在不代表所有用户都能冒领旧参与者身份。

## 10. 试玩数据回流与问题定位

### 10.1 目标与工作流

**DATA-01｜按需回流。** 当前开发在本地 Claude Code，服务器通过仓库与 Docker 部署。新增可重复执行的只读导出与拉取流程：服务器生成试玩报告 → SSH 拉回本地 → 开发 Agent 阅读摘要 → 按问题展开证据 → 修复并回归。不以手动下载整个数据库作为日常开发方式。

首版按需执行即可，不建设新的数据平台，不强制每天定时同步。完整备份属于独立运维功能，不与反馈报告混用。

**DATA-02｜报告内容。** 支持按派对、时间范围和问题筛选；至少包含构建／规则版本、参与者匿名标识、小游戏与题目版本、阶段和关键操作、错误、反馈、AI 任务状态与耗时、可获取的用量统计、积分结算及修正。先输出可读摘要与文件索引，细节分文件按需读取。

**DATA-03｜原地反馈。** 游戏内保留轻量“反馈问题”入口，能绑定题目、问答或当前操作；分类包括题意不清、答案疑似有误、不感兴趣、AI 判定有误、界面／流程异常。附言可选，不要求每轮填表，也不因未反馈阻止继续。

### 10.2 访问与隐私

**DATA-04｜只读最小权限。** 导出脚本使用只读能力和固定命令入口；本地拉取不执行生产迁移、删库或重部署。不要为方便 AI 把数据库端口直接暴露公网，不把广泛生产 SSH 权限当作默认测试工具。

默认剔除管理员密码、模型密钥、邀请令牌、会话凭据、Cookie 与无关个人信息。玩家采用一致化匿名 ID；公共报告和可分享样本不得混入隐藏状态。需要谜底或原始对话排查时，单独生成受控调试包，明确包含范围，不默认加入仓库。

**DATA-05｜数据使用边界。** 告知参与者会收集游戏反馈与必要诊断信息。不要静默把整场所有聊天发送给外部模型；默认仅选与问题相关的片段。提供本地保留／删除说明。

### 10.3 可复现性

**DATA-06｜从记录到复现。** 为需要复现的场景记录足够的初始状态／安全快照、事件顺序、随机与时间输入、实际模型结果、构建和内容版本。只有最终数据库状态不能声称可以完整重放。

开发 Agent 应把可复现的真实问题转换成回归用例。无法精确重放时，要指出缺失证据，生成最小近似复现场景，不报告“已完整复现”。本地复现使用隔离测试数据，不覆盖日常开发库或生产库。

## 11. 开发者与 AI 共用的多人测试环境

### 11.1 单人手动测试

**TEST-01｜一键多人房间。** 本地／专用测试环境能创建 2–8 个测试玩家，单界面切换观察与操作视角，减少手动开三个浏览器的成本。界面醒目标识测试状态；不取消正式游戏最低人数来伪造通过。

**TEST-02｜基础代操作。** 对纳入验收的玩法提供简单合法操作策略，填充等待玩家、投票、猜测等确定性动作；可暂停和人工接管。不需要给每个虚拟玩家配一个模型，也不把“智能陪玩”作为本版交付。

### 11.2 Coding Agent 使用

**TEST-03｜真实路径。** 测试员可以创建房间、加入／恢复身份、读取各自可见状态、批量执行操作、等待条件、收集结果。模拟玩家的动作走真实身份、HTTP／实时协议和权限检查，不能直接修改游戏状态来跳过业务流程。

服务端全知状态可用于测试断言，但与模拟玩家输入隔离。合法动作元数据可辅助 Bot；测试不能只验证框架自己列出的合法路径，还须覆盖越权、迟到、重复、断线与取消等反例。

**TEST-04｜浏览器验收。** 使用多个隔离浏览器会话验证真实页面：按钮是否可发现、输入能否提交、题主权限、秘密数据是否出现在网络响应、各视角是否同步。单界面身份切换和协议测试不能替代此层。

**TEST-05｜低 Token 输出。** 批量操作由程序执行，默认返回阶段摘要、断言、错误与证据路径；只有失败或明确检查视觉时读取截图、trace 和详细日志。单元测试继续运行，但不能作为“玩家流程已验收”的唯一证据。

### 11.3 模型测试与隔离

**TEST-06｜假模型与真模型分开。** 计分、权限、并发、恢复回归默认假模型／固定输出；真实模型用于海龟汤一致性、结构化工具调用和搞怪主持体验。结果明确标识模型、Prompt／工具版本、是否 mock、输入场景及成本信息。

海龟汤测试至少包含：标准是非题、否定／复合问题、前提错误、重复换种问法、信息不足、要求透露汤底、人工修正后继续提问。公开模型请求与公共 Agent 的提示词中检查是否误带秘密。

**TEST-07｜生产不开放调试。** 公网正式配置不得提供任意换身份、读手牌／谜底、直接写状态等接口。是否编入或开启由实施决定，但需要实际验证生产访问被拒绝；不能只把按钮藏起来。

**TEST-08｜人的试玩不可替代。** AI 测试可检查流程与文本表现，不能据此宣称朋友一定觉得有趣。搞怪模式需要真实朋友局反馈，特别记录是否有人主动找 AI、是否出现有意思的接话、是否需要开发者不断代操作。

## 12. 页面与基础视觉打磨

**UI-01｜电脑端优先。** 保留左游戏、右聊天／榜单布局。常用电脑尺寸下主要操作可见；右侧输入始终易找到，聊天不把积分或游戏控件挤出可用区域。手机保持基础可用，不进行全面移动端重设计。

**UI-02｜统一状态语言。** 大厅、选题、作答、等待、揭晓、结算、回顾使用一致的标题、按钮和错误样式。玩家应能判断“现在在哪一阶段、轮到谁、我能做什么、在等谁”。正在生成不等于正在等待其他玩家，需区别显示。

**UI-03｜游戏卡与封面。** 对现有游戏采用统一比例、排版和自制／可分发封面；名称与视觉体现机制，不复制商业原作的卡面或 Logo。不为每款游戏建立全新的美术体系，不把动画或形象包装作为主要工期。

**UI-04｜不破坏输入。** AI 新面板、聊天滚动与刷新快照不清空未提交文字，不抢焦点，不强制滚动离开当前操作。异步更新应指出变化，但不能覆盖题主已经确认的题。

**UI-05｜安全操作清楚。** “换一批”“跳过本题”“结束并结算”“放弃本场”“结束派对”不能共用一个含糊的退出按钮。破坏性操作提示影响范围；普通刷新和查看历史不弹重复确认。

## 13. 实施边界、数据兼容与发布

### 13.1 保留现有基础

沿用可用的游戏模块、权威运行时、持久化与模型适配边界。按当前仓库评估扩展，不重新开展一轮无边界的框架选型，也不默认推翻既有 Colyseus 或状态机实现。

技术实现可自主选择，但必须保持：游戏规则可测试，权威状态由服务端维护，所有变更有来源和权限，先持久化再对外确认，过期请求不跨场生效，分数不会重复入账。

### 13.2 基础数据关系

产品需要可关联：房间 → 派对 → 小游戏场次 → 回合／交互；题目版本与候选批次；玩家正式操作；模型任务与输出；基础奖励与调整流水；反馈与重放证据。具体表结构和 API 由研发决定，不要求按本节一比一建表。

模型生成结果、确认方案、计分策略和谜题改编都需要版本／快照，不能只保留“最新版”。历史视图应展示当时实际采用的内容。

### 13.3 旧数据与部署

**OPS-01｜数据不丢。** 升级前有备份与迁移说明；旧房间、玩家、聊天、已有成绩不得清空。旧版按原始分累加的记录应标记旧计分口径，不强行追算为新派对积分。建议新计分策略从新派对启用，旧活动场次沿用旧策略或由房主明确结束后开启新版。

**OPS-02｜自托管不回退。** 保持 Docker Compose 启动、持久卷、配置示例、健康状态与开发启动命令。未配置模型时基础固定玩法和题库仍可用；AI 海龟汤明确降级为人工主持，不承诺无模型也能自动判题。

**OPS-03｜接入不写死。** 模型由管理员配置，可按房间主持、裁判、题目改编选择不同策略；保留兼容网关／自定义地址的适配空间。不得依赖作者账户、未核验的免费额度或某个在讨论中出现的模型名才能运行。

**OPS-04｜发布许可不扩散。** 保留现有仓库许可与第三方声明，新增封面、题包和测试样本记录来源。不重新进行许可决策，也不把生产朋友数据发布为示例题库。

### 13.4 研发推进方式

先核对现状并给出差异清单，然后分批实际实现。建议顺序是：最小诊断与测试支撑 → 聊天／题主权限／候选完整流程 → AI 海龟汤与搞怪互动 → 派对结算／回顾／偏好 → 视觉统一与全流程回归。各批可调整，但不应把“还有一个技术选择”变成长期只写计划。

普通工程细节按建议默认落地并记录。仅在不可逆数据迁移、权限改变、明显扩大范围、真实额外费用或产品要求冲突时停止并提出具体问题。不得将未运行的测试写成通过。

## 14. 验收清单

每项提供可复现步骤、结果及对应证据路径。以下是最低场景，不是唯一测试集。

### 14.1 房间、偏好与 AI

| 编号 | 场景与通过条件 |
| --- | --- |
| AC-01 | 同一邀请房间跨两次派对使用：身份可恢复，第二场积分为零，第一场完整回顾仍存在。 |
| AC-02 | 所有人退出或跨日后再来：不自动结束派对；服务重启保留已确认状态，计时按恢复策略继续。 |
| AC-03 | 大厅直接开玩与调整偏好都可用；中途回大厅调整不清积分、不修改已玩题，新主题影响后续候选。 |
| AC-04 | 普通发送不调用模型；发送并找 AI 调用一次并公开消息；手写 @AI 仍兼容，不需成员补全。 |
| AC-05 | 多人连续请求不重复执行变更；AI 工具失败或无权限时如实说明，不虚报已修改。 |
| AC-06 | 同一场景测试普通／搞怪模式：基础口吻自然，搞怪更愿意协商和提出意外方案；系统权限不改变。 |

### 14.2 选题、秘密与海龟汤

| 编号 | 场景与通过条件 |
| --- | --- |
| AC-07 | 非房主题主独立完成候选选择、刷新、手写与确认；非题主越权确认被服务端拒绝。 |
| AC-08 | 第一个题主未选的卡，第二个题主能在历史找到并使用；刷新浏览器仍在；已玩题明确标记。 |
| AC-09 | 右侧要求新主题，左侧出现有效题卡；等待期间选了旧题后，迟到生成不能覆盖它。 |
| AC-10 | 候选历史、公共聊天、工具返回和网络消息均无不该公开的答案／词对；自定义答案走私密输入。 |
| AC-11 | 事实题锁定答案快照和口径；朋友偏好在他人猜测前锁定；查不到答案不伪造成已验证。 |
| AC-12 | 海龟汤玩家在左侧提交，AI 自动对相同记录判定，全体看到结果，不需去右侧再次呼叫。 |
| AC-13 | 海龟汤固定问答集及同义问题测试可审查；人工修正保留并影响后续判定；索要汤底未泄露。 |
| AC-14 | 模型失败／取消／切题／重启时，问题不串题、不重复判定入账；可以重试或知情转人工。 |
| AC-15 | 母题改编有允许替换项与因果约束；至少展示一个通过案例和一个被拒绝／回退案例。 |

### 14.3 Canvas、结算与回顾

| 编号 | 场景与通过条件 |
| --- | --- |
| AC-16 | Agent 完成“多人填主题 → 匿名投票 → 题主选题”的动态组合；提交、结果和取消可恢复，非静态演示。 |
| AC-17 | 小游戏原始成绩与派对积分分离；按同一策略排名奖励；并列、阵营、贡献缺证和未参与者均有明确结果。 |
| AC-18 | 无限轮玩法可正常结束并结算；放弃本场不发基础派对积分；双击、重连、重试不重复奖励。 |
| AC-19 | 玩家要求给某人额外加／扣分，AI 生成可见方案；未确认不生效，房主批准后准确入账，可出现负总分。 |
| AC-20 | 取消／替换／过期调分方案不能执行；更正采用追加流水；原始成绩和调整理由可追溯。 |
| AC-21 | 完整回顾包含最终排名、逐场战绩、调整与关键事件；AI 总结失败不影响历史查看和开启下一场。 |

### 14.4 工具与交付

| 编号 | 场景与通过条件 |
| --- | --- |
| AC-22 | 从服务器按派对拉取一次脱敏报告；本地 Agent 定位到具体问题和版本；导出不包含凭据、不修改生产。 |
| AC-23 | 单人创建多玩家测试房间并接管不同视角；真实隔离浏览器完成一次多人流程，生产调试入口被拒绝。 |
| AC-24 | Coding Agent 批量执行动作并产出摘要／证据；至少一个真实试玩问题转成回归用例，不能复现时说明缺失。 |
| AC-25 | 升级迁移后保留旧数据；新旧计分口径不混用；无 AI 配置仍能跑基础玩法；Docker 启动说明可复现。 |
| AC-26 | 大厅和主要游戏路径完成电脑端视觉验收：封面一致、阶段与等待对象清楚，AI 更新不破坏输入。 |

### 14.5 真实朋友局与版本完成

建议以 4 位朋友、约 60 分钟的真实聚会验证端到端体验；这是场景建议，不是必须精确凑时长。至少跨两款游戏，覆盖非房主题主、候选历史、AI 海龟汤、一次自愿的搞怪协商、小游戏结算和完整派对回顾。

记录 AI 是否被朋友主动使用、哪些回答有趣／八股、等待在哪里打断节奏。允许出现不够好笑或被纠正的回复，但不能有阻断、秘密泄漏、错误越权、不可恢复进度或重复计分。

交付必须同时提供自动化结果、浏览器流程证据、真实模型试跑、朋友试玩反馈和已知问题。未拿到模型密钥、SSH 或真实朋友局时，明确将相关验收标为未执行；不得靠 Mock 宣称全量验收通过。

## 15. 建议默认与需求变更记录

### 15.1 可直接采用但需在交付列明的默认值

| 项目 | 建议默认 |
| --- | --- |
| 试玩主持模式 | 新测试派对默认搞怪；正常房间沿用上次选择；始终可切换。 |
| 候选展示 | 默认 3 张；同场同类型历史可回看；已玩默认不推荐重复。 |
| 派对主题调整 | 所有人可提议，汇总展示；房主确认本次共同配置。 |
| 跳题投票 | 当前题有效参与者严格多数；参与集合在发起时固定，房主可直接处理。 |
| 名次奖励 | 第 8.2 节 0–10 相对名次表，集中配置；并列均分，保留 1 位小数。 |
| 缺少贡献依据 | 不编造排名，默认并列并允许朋友协商；不强制互评或要求理由可信。 |
| 正式积分入账 | 小游戏结算页接受默认／批准方案时一次入账；未批准提议不生效。 |
| 海龟汤问题 | 同谜题串行判定，单题可重试；困难或欠明确问题允许澄清。 |
| 房主离线 | 不自动转权；显式转交／管理员恢复；已保存状态不丢失。 |
| 导出与测试 | 按需 SSH 拉取；默认脱敏、只读；Mock 回归与真模型验收分离。 |

这些默认值不是新一轮讨论清单。研发可以采用并在变更记录中注明；实际冲突再针对性提出，不阻塞整个版本开始。

### 15.2 对旧讨论的明确覆盖

**一个万能 AI → 分职责。** 左侧海龟汤裁判独立于右侧 Room AI；标准提问留在左侧，不以“统一聊天入口”为由搬走。

**只有房主能操作 → 按阶段授权。** 房主管理全局，当轮题主控制其选题；不是给所有玩家管理权限。

**固定题直接开始 → 可选的准备阶段。** 玩家可选、刷、回看、手写；固定卡牌不受影响。

**原始得分全局相加 → 按名次奖励。** 同时保留原始战绩，旧数据不静默追算。

**严肃贡献算法 → 基础记录加自由协商。** 玩家互评可通过聊天、提议或必要投票表达，不新增每局必填问卷；支持经批准的负分和夸张调整。

**普通严肃／搞怪搞笑 → 同人格、不同冒险倾向。** 两种模式都自然，搞怪本次重点验证；规则事实与权限仍可靠。

**初始化仪式 → 大厅可重入的偏好流程。** 不强制、不清零，不开发动画。

**单测通过即完成 → 真实链路与朋友局验收。** 保留单测，增加多视角浏览器、真实模型、生产反馈与复现证据。

长期保留“AI 游戏之神、外部棋盘、道具技能和跑团式自由编排”的愿景，但不进入本次实施范围。
